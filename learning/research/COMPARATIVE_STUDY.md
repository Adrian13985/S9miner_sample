# 对标课程研究与路线决策

## 为什么不能选一套教程照搬

完整性有四个互相独立的维度：知识覆盖、教学顺序、版本可复现性、板卡可执行性。现有资料各自只强在其中一部分，因此本项目采用“课程结构综合”，不把任何一套教程当作唯一答案。

## 从各资料吸收什么

### 从 AX7010 吸收覆盖面

AX7010 的课程目录证明一条较完整的 Zynq 路线至少应包括：

- RTL、仿真、时钟、RAM/ROM/FIFO、按键消抖、PWM 和串行协议；
- PS 裸机、GIC/Timer、MIO/EMIO、AXI GPIO、自定义 IP、UART、Ethernet；
- PL 访问 DDR、BRAM 共享、AXI DMA、Scatter/Gather DMA；
- FreeRTOS、HLS；
- PetaLinux、设备树、用户态应用、字符/platform/中断/DMA 等驱动主题。

本项目不需要照搬 HDMI、摄像头和特定扩展模块，但必须保留它们背后的通用节点：像素流、帧缓存、AXI-Stream、VDMA、吞吐预算和外设驱动模型。

### 从 Zynq Book 吸收递进方式

它把学习组织为：最小 PS+PL 系统 → 增加中断 → HLS → 多种自定义 IP → 完整音频系统。这说明综合项目应该建立在几个可解释的小系统上，而不是一开始堆 IP。项目路线据此设置了 AXI GPIO、PL 中断、自定义寄存器、Stream/FIFO、DMA，再进入板卡综合控制。

### 从 AMD 官方教程吸收端到端边界

UG1165 把 PS-only、调试、Linux、GP/HP 端口、CDMA、启动、自定义 AXI IP 和 Linux 驱动连成一条链。因此本路线同时保留裸机线和 Linux 线，并要求每次指出交付物变化：BIT/HDF/ELF/BOOT.BIN、U-Boot、设备树、内核和根文件系统各负责什么。

### 从 Zybo Z7 吸收工程化交付

Zybo Z7-10 使用同一 XC7Z010-CLG400。它的工程展示了 Tcl 重建、硬件交付、软件工程和 PetaLinux 工程的分层，以及 DMA/时钟问题的真实故障记录。本项目后续实验要逐步从不可移植的 `.xpr` 快照过渡到“源码 + XDC + Tcl/步骤 + 验证记录”。

### 从官方驱动代码吸收版本一致性

例程只负责展示 API 组合，不自动适合本板。学习顺序是：先在 `xilinx-v2017.4` 找同版本例程 → 阅读本项目 BSP 中实际生成的驱动 → 追到寄存器/协议 → 重新设计本板实验。这样既避免拿新版 API 硬塞旧 SDK，也避免把厂商例程当作设计答案。

## 最终路线结构

```text
工具与证据
  -> 嵌入式 C + Cortex-A9 执行模型
  -> RTL + Testbench + XDC + STA
  -> PS 裸机外设 + 时间 + 中断
  -> 启动 + SD/FatFs
  -> MIO/EMIO/AXI-Lite + 自定义 IP
  -> AXI-Stream + BRAM/DDR + DMA + Cache
  -> 以太网 + RTOS
  -> U-Boot/Linux/设备树/驱动
  -> S9 板卡系统项目
  -> HLS/PYNQ/性能优化选修
```

这条路线有三条并行线：

- **原理线**：数字逻辑、CPU/内存、总线、协议、OS。
- **实验线**：从安全 LED/UART 到 PS–PL、DMA、网络、Linux。
- **证据线**：预测、仿真、日志、波形、故障注入、无提示重建和迁移。

只有三条线在里程碑处汇合，才算完成阶段；跑通下载文件只完成实验线的一小部分。

## 不纳入主线的内容

- 挖矿算法、矿池协议和商业固件逆向：与 Zynq 通用能力不同，且会过早引入高功率硬件风险。
- 直接刷写 NAND：在完成备份、恢复和启动链理解前不进入实验主线。
- 一开始使用 PYNQ 隐藏底层：PYNQ 保留为验证/快速原型分支，先完成 MMIO、AXI、DMA 和 Linux 基础。
- 因本板无对应接口而硬搬 HDMI/音频/摄像头：只抽取 Stream、DMA、帧缓存和吞吐设计等可迁移知识。
