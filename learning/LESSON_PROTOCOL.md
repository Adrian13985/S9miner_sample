# 统一教学与验收协议

## 一次学习会话的结构

### 1. 定位

- 指出当前课程节点、直接先修和项目锚点。
- 说明本次只解决哪一个可验证问题。
- 从 `MASTERY.md` 读取已有证据，不用学习者的主观熟悉度代替诊断。

### 2. 先预测

在解释前要求学习者预测一个现象、画一条路径或写一个最小片段。第一次接触的新知识可以先给最小背景，但不要直接给完整答案。

### 3. 建立因果模型

按需贯穿以下层次：

```text
外部世界/存储介质
-> 管脚、控制器或PL逻辑
-> 时钟/复位/寄存器/FIFO/协议
-> AXI与地址空间
-> Cortex-A9、异常、Cache或DDR
-> BSP/驱动
-> C应用状态
-> 串口、LED、文件、波形或测量值
```

每次至少说明：为什么有效、依赖哪些假设、哪里最容易坏、如何观测。

### 4. 项目实验

- 先保存已知可工作的基线。
- 一次只改变一个关键变量。
- 写出修改前预测和可观察结果。
- 编译警告、返回值、硬件现象和时间行为都属于结果。
- 失败时先定位层级，再决定查看哪份源码或手册。

### 5. 形成掌握证据

按需从下列证据中选择，不要求每次全部完成：

- 无提示口述或路径图；
- 无参考最小重写；
- 给定故障现象定位原因；
- 解释API下一层的寄存器或协议行为；
- 修改约束后的近迁移；
- 换表面场景但保留底层结构的远迁移；
- 隔日或隔周复测。

### 6. 收尾

- 更新 `MASTERY.md` 中的真实证据。
- 把错误模型写入 `MISCONCEPTIONS.md`，不要只记录答案。
- 把需要延迟复测的内容加入 `REVIEW_QUEUE.md`。
- 下一课由证据缺口决定，不由例程编号自动决定。

## 解释代码时禁止的捷径

- 不把逐行翻译当成底层解释。
- 不因代码能编译就宣称硬件行为正确。
- 不因驱动API存在就跳过地址、状态位和时序条件。
- 不把 `volatile` 当作原子性、互斥、Cache一致性或内存屏障。
- 不引用其他开发板的管脚或电压配置替代本板核验。
- 不把生成代码全部当作必须掌握；只追踪当前问题需要的路径。

## 标准输出骨架

```markdown
## 本次问题与课程位置
## 先修诊断/预测
## 底层因果链
## 当前项目中的对应位置
## 边界条件与故障模式
## 实验与观测
## 近迁移/远迁移
## 掌握证据与下次复测
```
