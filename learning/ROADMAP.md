# 基于证据门槛的学习路线

这不是固定“第几周看第几章”的日历。每个阶段先取得退出证据，再进入依赖它的阶段；时间由实际学习速度决定。并行支线只能在不掩盖主线缺口时进行。

## 总体阶段

| 阶段 | 目标 | 项目范围 | 退出门槛 |
|---|---|---|---|
| 0. 建立基线 | 能恢复、能观测、能说清工程产物 | P00–P04 审计 | 独立重建一次现有工程；保存版本、日志、跳线和恢复说明 |
| 1. RTL 基础 | 不依赖 CPU 做出、验证并约束 PL 逻辑 | P05–P08 | Testbench 自检通过；上板结果与时序报告一致；能故障注入 |
| 2. PS 裸机基础 | 理解启动、MMIO、时间和中断 | P09–P13 | 独立完成非阻塞事件系统，并画出 IRQ 完整生命周期 |
| 3. 存储与启动 | 可靠读写、制作和诊断启动镜像 | P14–P16 | 修复 P03；完成可移植 BIF 和 SD 冷启动；能定位至少两种失败 |
| 4. PS–PL 控制面 | 用 AXI-Lite/IRQ 建立可维护硬件接口 | P17–P22 | 自定义寄存器 IP + 驱动 + PL 中断 + BRAM 数据交换均可复现 |
| 5. 数据面与性能 | 掌握 Stream、DDR、DMA、Cache 和测量 | P23–P27 | 轮询/中断 DMA 可解释；能预测并测量瓶颈；处理背压与错误 |
| 6. 通信与实时 | 建立 Ethernet 和 RTOS 的并发模型 | P28–P30 | PHY/GEM/lwIP 数据链可观测；RTOS 任务/ISR 所有权清楚 |
| 7. Linux | 从启动到设备树和驱动 | P31–P35 | 能从源码构建并启动；完成一个有 IRQ 的 platform driver |
| 8. 板卡系统化 | 把能力迁移到 S9 板独有资源 | P36–P40 | 完成跨层项目、故障矩阵、性能报告和无提示答辩 |
| X. 选修 | HLS、PYNQ、双核、远程更新 | X01–X05 | 先满足对应主线先修；输出与手写/裸机/Linux 方案的比较 |

## 阶段 0：现有项目不再只是“能跑”

1. P00 建立硬件/软件基线与恢复卡。
2. P01 UART 做闭卷路径图、阻塞故障注入和独立重写。
3. P02 GPIO 核对原理图、电平、MIO Bank 和驱动寄存器。
4. P03 只做代码审计，不把存在越界的版本作为成功例程。
5. P04 区分 JTAG 启动和 SD 启动，识别 BIF 的绝对路径问题。

阶段成果是可信基线，不是“复习四个例程”。

## 阶段 1：先建立 FPGA 思维

用 PL LED 和 PS FCLK 完成 RTL/仿真/XDC/STA 主线，避免一开始依赖板载 PL 晶振是否装配。顺序为组合/时序 → 自检 Testbench → 约束 → 复位 → 消抖/PWM → ILA。只有能在仿真中解释每个周期，才进入 AXI IP。

## 阶段 2：建立 CPU、驱动和中断因果链

以同一功能做三次实现：主循环轮询 → 定时器节拍状态机 → UART/GPIO 中断事件化。重点不是 API 数量，而是状态在哪里、谁修改、何时可见、如何超时、如何清除中断源。

## 阶段 3：先修复，再学习启动

P03 的越界读和 `br/bw` 缺失先作为 C/文件系统案例修复。之后才进入 BootROM、FSBL、BIF、bitstream 可选性和冷启动。整个阶段只写可恢复 SD 卡，不擦 NAND。

## 阶段 4：控制面先于数据面

先比较 MIO、EMIO 和 AXI GPIO，再实现 AXI Timer 和自定义 AXI-Lite 寄存器。寄存器需要版本、能力、状态、W1C/RO 等明确语义。PL 中断必须有保持/清除契约，最后用 AXI BRAM 展示批量共享数据与寄存器控制面的差别。

## 阶段 5：从 `ready/valid` 到 DMA

先用 RTL/Testbench/ILA 证明背压和 `TLAST`，再连接 AXI DMA。先 simple polling，后 interrupt，再 SG；每一步都明确缓冲区所有权和 Cache 维护。性能实验同时测吞吐、延迟和 CPU 占用，不能只报“成功”。

## 阶段 6：通信和 RTOS

先通过 MDIO 读取 PHY ID、协商状态和链路速率，再进入 GEM/lwIP。RTOS 以已有中断/状态机为迁移对象：ISR 只产生事件，任务承担协议和 I/O；通过过载测试验证 queue 满、超时和 watchdog。

## 阶段 7：Linux 不从写驱动开始

顺序是 FSBL/U-Boot/kernel/DTB/rootfs → 设备树 → 用户态 GPIO/UIO → 字符设备 → platform driver → IRQ/poll → DMA API。使用 S9 主线设备树作为板级事实起点，但固定同一发行线，不把当前 `master` 与 2017.4 混编。

## 阶段 8：S9 专项项目

优先做无外接高功率设备的板级诊断器和 PL→DMA→网络数据管线。风扇和 9 路算力板接口属于高风险支线，必须先仿真/内部回环并完成电气核验。毕业项目必须包含：架构理由、吞吐/时延预算、恢复方案、故障注入、可复现构建和迁移答辩。

## 复习与迁移节奏

每个核心节点在以下时间点复测：完成当天、1–3 天、1–2 周、进入下游项目前。每次复测换一种表面任务：

- 解释 → 预测；
- 预测 → 无提示重写；
- 重写 → 故障定位；
- 同外设 → 换 API/执行方式；
- 同结构 → 换成另一个外设或 Linux/RTOS 层。

若延迟复测失败，先回到对应节点，不通过继续堆新例程掩盖缺口。
