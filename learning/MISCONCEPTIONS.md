# 错误模型记录

这里记录“为什么会错”，而不只是正确答案。状态只有在新的独立证据出现后才能改为已纠正。

| ID | 容易形成的错误模型 | 更准确的模型 | 当前状态 | 纠正证据 |
|---|---|---|---|---|
| M01 | bitstream和ELF都是“下载程序” | bitstream配置PL硬件；ELF由Cortex-A9执行，修改一方不一定需要重建另一方 | 待复测 | 闭卷比较两种修改流程 |
| M02 | GPIO编号就是封装管脚号 | XGpioPs编号、MIO/EMIO、PL管脚和封装球位属于不同映射层 | 待验证 | 用P02和原理图完成一次端到端映射 |
| M03 | `inbyte()`只是普通函数调用，不会影响调度 | 它可能阻塞；是否调用取决于FIFO状态，阻塞会停止同一执行流中的其他工作 | 已用辅助实验纠正，待延迟复测 | 2026-09-21 P01故障注入：无输入时周期打印停止，见 `evidence/P01_UART/2026-09-21_blocking_fault_observation.md` |
| M04 | `volatile`可以解决并发问题 | 它主要约束编译器访问，不能自动提供原子性、互斥、Cache一致性或顺序保证 | 未开始 | Timer/IRQ与DMA阶段分别验证 |
| M05 | 指针参数包含缓冲区长度，或把 `*p`/`&p` 都理解为“取地址” | C指针通常不携带容量；`p` 保存目标地址，`*p` 解引用目标，`&p` 取得指针变量自身的地址 | 2026-09-23 延迟复测再次暴露；分步后局部纠正，待无提示复测 | 2026-09-21 P01指针问答；`evidence/P01_UART/2026-09-23_independent_retest.md`；后续修复P03越界并检查 `br/bw` |
| M06 | 文件API返回成功就代表完整读写 | 还必须检查实际字节数、关闭结果、错误路径和目标缓冲区终止符 | 已暴露 | P03修复后上板日志 |
| M07 | Verilog语句像C一样按顺序运行 | RTL描述并行组合/时序硬件，赋值语义受时钟和过程类型影响 | 未开始 | Testbench波形与预测题 |
| M08 | DMA完成后CPU一定能看到最新DDR数据 | Cache、方向、对齐和维护操作会影响CPU与DMA观察到的数据 | 未开始 | DMA故障注入与校验 |
| M09 | 当前 UART 接收经过中断，`count` 是 UART 寄存器中的值 | 当前 P01 由 CPU 轮询状态寄存器并读取 RX FIFO；`command` 和 `count` 是 C 对象，未经过 GIC/ISR | 已暴露，经提示纠正，待闭卷复测 | 2026-09-21 首次 UART 路径回答；见 `evidence/P01_UART/2026-09-21_blocking_fault_observation.md` |
| M10 | LSW/MSW 是“高低 8 位”，或每个 GPIO 都有独立寄存器地址 | 每个 Mask/Data 寄存器是 32 位：高 16 位为低有效掩码、低 16 位为数据；同一 Bank 半区的 16 个 GPIO 共享一个地址 | 引导后即时迁移正确，待晚间闭卷复测 | 2026-09-22 GPIO69/70 边界题和 GPIO70/71 多位写题 |
| M11 | 两个寄存器地址相邻就能由一次 32 位写入同时更新 | 一次 `Xil_Out32` 只访问一个 32 位寄存器；地址相邻只表示内存映射连续，跨寄存器仍是两个总线事务并存在中间状态 | 引导后已纠正，待晚间闭卷复测 | 2026-09-22 LSW/MSW 跨边界状态题 |
| M12 | `OUTEN=0` 时 `WritePin` 不会更新输出数据 | DATA 锁存、DIRM 方向和 OUTEN 输出驱动是分层控制；关闭 OUTEN 时 DATA 仍可预装载，重新使能后立即驱动该值 | 引导后已纠正，待晚间闭卷复测 | 2026-09-22 无毛刺 LED 初始化题 |
| M13 | bit 编号可直接写成十六进制数值，例如 bit 5 对应 `0x05` | bit n 的单 bit 掩码是 `1U << n`；bit 5 为 `0x20`，bit 3 为 `0x08` | 2026-09-23 延迟迁移未通过；表达式正确但手算把 bit 1 当成 bit 0 | 2026-09-22 DIRM 并发题；`evidence/P02_GPIO/2026-09-23_rmw_delayed_retest.md` |
| M14 | 共享寄存器的读—改—写天然安全，或临界区应持续到主循环结束 | 读—改—写可能被中断插入并由旧快照覆盖新值；临界区只覆盖必要的读、修改、写，并恢复进入前的中断状态 | 2026-09-23 延迟迁移未通过；仍写 `restore_irqs(enable)` 并残留 DIRM 模板 | `evidence/P02_GPIO/2026-09-23_rmw_delayed_retest.md` |
| M15 | `br` 小于请求量就表示读取失败 | `FRESULT` 表示操作状态；在文件末尾，`FR_OK` 且 `br < requested` 可以是正常短读。应用必须结合返回码、实际字节数和上下文判断 | 2026-09-24 经一次纠正后能在后续场景中正确判断，待延迟复测 | `evidence/P03_SD_FATFS/2026-09-23_foundations_preview.md`、`2026-09-24_fatfs_foundations_lesson.md` |
| M16 | 把 `br` 当成最后一个有效下标，而不是实际字节数量 | `br=N` 表示有 N 个有效字节，下标为 `0..N-1`；文本终止符在容量允许时写入 `dest[N]` | 2026-09-24 延迟自由回答已正确给出数量、最后下标和终止符位置；待一周后变式复测 | `evidence/P03_SD_FATFS/2026-09-24_fatfs_foundations_lesson.md`、`2026-09-24_delayed_micro_retest.md` |
| M17 | 把 `br` 的原始字节数等同于 `strlen`，或认为数据中的 `\0` 会改变 FatFs 的读操作结果 | `f_read` 按请求量和文件状态复制原始字节并通过 `br` 报告数量；`strlen` 只是应用层从缓冲区开头数到首个 `\0`，二进制校验应使用已知实际长度 | 2026-09-24 无选项变式正确区分 `strlen=2` 与原始长度5；待一周后再测 | `evidence/P03_SD_FATFS/2026-09-24_delayed_micro_retest.md` |
| M18 | 在预测 `bw/br` 时把被修改的变量答成函数名，尚未稳定区分调用函数和调用者输出对象 | `&bw` 把调用者对象的地址传入输出参数；写函数通过该地址修改 `bw`，读函数同理修改 `br`；请求长度与实际传输量须分别判断 | 本次上板前预测仍错误，经提示后能答出 write→bw、read→br；待无提示迁移 | `evidence/P03_SD_FATFS/2026-10-16_sd_not_ready_debug_session.md` |

新增误区时填写触发现象、当时推理和修正实验；不要把所有常见错误预先堆入本表。

## 2026-10-16 诊断结论校正与待验收点

以下是本次调试中 AI 讲解或推断需要校正的边界，不直接归为学习者已独立暴露的错误，也不记作已掌握：

- `f_mount(&fatfs, "", 0)` 为延迟挂载；`success to open SD Card` 不能证明卡通信正常。原版打印的 `256` 是请求量，读取失败后 `%s` 打出的 `€` 是无效缓冲区内容。
- `XSdPs_IdentifyCard()` 在 CMD1 失败时也可能按 SD 分支返回成功，故 `IdentifyCard=0` 不证明有效响应。`CfgInitialize=0` 同样不证明外部 CLK/CMD 波形正常。
- 修改为 LVCMOS25 是依据原理图的配置修正，未改变物理供电；再次有效运行仍失败，不把它写成已解决的根因。
- 选中平台 `_2` 不等于已下载应用；SDK 曾清空 Application 并使 `no_download=true`，造成仅 `ps7_init` 而无 `dow/con`。必须同时验证平台、脚本、ELF 和运行日志。
- C154 对地 3.34 V 只确认该卡供电测点；尚无 U6 各电源、地连续性、CMD/CLK 连通性和时序的测量证据，不能宣判硬件损坏。
